# 如何验证这些 Skills

验证分三步，分别回答不同问题。

1. **结构检查**：在仓库根目录运行 `python -X utf8 -m unittest discover -s tests -p "test_*.py" -v`。它检查四个入口的名称与描述、本地文件链接、公开借鉴出处、绘图脚本的基本输出，以及 PDF 脚本的语法、帮助和报错。通过表示这些文件与接口正常，不代表模型会照着写，也不等于完成一次 PDF 导出。
2. **显式调用**：用 [behavior_cases.md](behavior_cases.md) 的 D/P/E/M 八题，各开一个新会话，明确写 `$skill-name`。按每题四个检查点打分，保存实际回答。这样检验 Skill 已被明确加载时的输出。
3. **自动选择**：用 R1、R2 在新会话中不写 Skill 名称，检查系统选用的任务方法和最终产物。看不到内部选择记录时，只能依据可观察的行为判断，不把推测写成“已激活”。

单题暂以 **至少 7/8 分、没有 0 分检查点、没有直接失败项** 为通过；四个 Skill 各自两题均通过，才称该 Skill 通过本题库。R1、R2 单独报告，不能用明确调用的成绩替代自动选择成绩。这个阈值是本仓库的回归判据，不是对所有论文和实验场景的质量保证。

建议同时用相同提示做一次不启用该 Skill 的对照，比较它解决了哪些具体缺点。测试应使用同一模型、相近设置与同一份输入；模型输出有波动时重复失败题，不凭一次漂亮回答宣布稳定有效。若任务要求 PDF，还要打开实际 PDF 检查中文、公式、图文邻接和分页；Markdown 文件存在不等于导出成功。

每次运行记下日期、Skill 文件版本或提交号、调用方式、实际输出、四项分数和失败原因。行为题的材料均为虚构，不需发布用户的真实研究资料。`quick_validate.py` 可另用于检查 Skill frontmatter；它与这里的结构检查一样，不评判写作质量。
